# 后台 Runner 运维

模型测试生成、语音识别、视觉生成、Galgame 标注导入和视频导出均由同一进程内的轮询 Runner 执行。
Runner 不是独立服务，也不应在多进程间共享同一 SQLite 任务队列。

## 存活与退避

每个 Runner 的单轮异常只记录 Runner 名称、任务标识和异常类型，不记录密钥、媒体内容或供应商响应
正文。失败后采用有上限的指数退避；任一成功轮会把连续失败计数清零。应用启动部分失败时，已经
启动的 Runner 会按逆序停止，避免留下半启动后台任务。

`GET /health` 只检查 Web 进程可响应。`GET /ready` 还要求数据库可用、Supervisor 已启动且全部
Runner 存活；Runner 未启动、循环退出或连续失败达到 3 次时返回 503，健康时继续返回现有
`{ "status": "ready", "schema": "..." }` 结构。

## 排查顺序

1. 查看应用日志中的 Runner 名称、任务 ID 和异常类型；不要开启供应商响应正文或媒体内容日志。
2. 检查磁盘空间、运行期目录权限、FFmpeg/FFprobe/Chromium 等本机依赖和供应商 HTTPS 地址。
3. 调用任务详情 API 确认任务阶段、错误和 revision；不要直接修改任务表。
4. 若只是瞬时错误，等待退避重试和下一次 `/ready`；恢复成功后连续失败计数会自动清零。
5. 若循环已退出或配置已修正但仍不恢复，正常重启单机应用。启动恢复逻辑会按各任务类型的既定
   规则处理 `running` 状态，避免重复付费提交。

关闭应用时 Supervisor 会停止所有 Runner。强制终止可能留下运行中记录，应由启动恢复逻辑处理，
不得用 SQL 把任务手工改为完成或失败。
