# Agent Note: 成片解码资源回收与失败诊断

Status: implemented

## Problem

长时间线的顺序编码为每个历史片段保留 FFmpeg 解码进程、管道与末帧，直至整条成片结束。内存随已播放镜头数累积，默认自动线程还会增加每个解码器的缓冲。正式 Rendering 在 1.5 GiB 上限下发生 OOM，两个约 70 秒的 1080p60 任务分别停在 34% 和 36%。失败被统一改写成“剪辑成片渲染失败”，且没有后台诊断；解码器异常退出还可能被上一帧保持逻辑掩盖。

## Decision

`timeline_ranges.frame_clips` 提供当前时刻的可见片段，包含接缝窗口中超出名义片段边界的两侧把手。成片编码在每帧打开新源前回收集合之外的解码器和图片缓存。解码器关闭同时释放管道、诊断句柄与末帧；同素材的多个片段仍独立维护播放游标，不能按素材 ID 合并资源。

视频解码、编码及音频输入和输出固定最多两个编解码线程，普通滤镜和音频复合滤镜固定一个线程，避免按宿主 CPU 数扩大帧缓冲。成片规格、CRF、帧采样、接缝保持与音频时间线保持原规则。

FFmpeg 标准错误写入随子进程回收的临时文件，异常时仅取尾部 4000 字节，避免错误管道填满导致死锁。解码短读核对进程退出码，成功 EOF 才允许沿用已有末帧；非零退出、无完整首帧和部分原始帧明确失败。编码断管读取实际退出原因，取消优先保留取消语义。

`render_errors.py` 区分视频解码、画面编码、音频合成、内存不足和磁盘不足；SIGKILL 提示“可能是内存不足”，不把所有系统终止断言成 OOM。失败回执附任务短编号，沿现有 Video 回执与任务页展示。FFmpeg 退出码和诊断只写服务日志；未知异常仅记录类型和不含异常正文的调用栈，避免把路径、供应商正文或凭据返回页面。镜像本地媒体闭包显式登记新错误模块，并补齐现有翻页模块。

## Alternatives considered

- 只提高正式容器内存上限：推迟故障，不能限制历史解码器的线性累积，且增加宿主内存压力。
- 每帧重启全部解码器：资源有界，但重复探测和寻址成本高，也增加连续采样错位风险。
- 只按片段名义结束时间清理：会过早回收接缝窗口仍需要的出场把手。
- 把原始异常直接显示给用户：可能泄露路径和上游响应，提示也不稳定。

## Consequences

资源数量由同时可见片段和接缝决定，而非时间线总片段数决定；大量同时叠加图层仍需要与画幅相应的内存。固定线程数可能降低 CPU 充足环境的峰值吞吐。单个 FFmpeg 或 Python 被系统终止时仍可能需要服务生命周期恢复；本次不改变持久队列的恢复规则，不更改数据库或公开字段。

## Verification

- 媒体服务、取消、连续采样、书页翻页和方向转场共 175 项测试通过；架构检查 125 项通过。
- 新增真实 FFmpeg 十二镜头回归：硬切最多保留一个解码器，交叉淡化最多两个；全部 72 帧保持有效画面，退出后进程、管道和末帧全部释放。
- 故障覆盖解码器 SIGKILL、超过管道容量的标准错误、内存不足、磁盘不足及未知异常的安全回执和日志。
- 在无网络、无正式数据挂载、2 CPU、1.5 GiB 内存上限的容器中编码十镜头 1080p60，交替使用眼睑和翻页转场：7.5 秒、450 帧，H.264/AAC 规格与时长校验通过；峰值 855277568 字节（约 816 MiB），OOM 与 OOM kill 均为零。
- 修改范围 Ruff 检查和格式检查通过。测试证据位于被忽略的 `.local/render-memory-fix/`。
- 用户另在“排查渲染失败与内存占用”聊天切换本机热加载入口，并明确要求正式服务保持关闭。因此本次未启动或切换正式服务、未更改正式配置、未重新提交原视频；原视频导出待本机入口恢复后完成。
