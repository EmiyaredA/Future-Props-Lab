# Agent Note: 连续接缝的预览播放器与精确画面交接

Status: implemented

## Problem

节目监视器按 clip.id 挂载视频，两个同素材且源时间连续的片段交接时会销毁已解码播放器，新的 video 元素从空画面开始。精确停帧又按每个请求 URL 重新挂载并先隐藏图片，旧帧立即消失，新帧异步加载期间露出空播放器，因此没有时间线空隙的接点也会闪黑。

只读诊断中，APTMV-冈牧-V2 revision 1194 的左片段在 16,199,838 微秒结束，右片段同一时刻开始；同素材的源时间在 3,691,410 微秒连续，没有转场。原素材在接点前、接点上和接点后的正式合成结果均非黑帧。另一个问题是暂停拖动时跳过正在 seeking 的播放器后，没有回调补齐最新目标，停止拖动可能停在旧位置。

## Decision

`previewPlayback.ts` 根据可见画面轨的相邻区间、素材、速率、循环标志和连续源时间生成播放器身份。连续分割复用原 video 元素；视觉转场伙伴保持独立身份，以便同时参与画面；跳剪和真实空隙不合并。

`VideoEditorPreciseFrame.tsx` 同时持有已加载画面与当前待加载图片，当前请求加载成功后原子替换。过期或已卸载请求不能更新显示；失败保留上一张画面并明确提示。等待期间显示“画面更新中…”，提示消失才表示当前时刻的精确帧就绪。缓存局限于当前工程和保存版本，播放、实时变换草稿与版本变化仍清空对应显示。

代理视频在 loadedmetadata 与 seeked 时重核当前目标；暂停情况下补齐被前一次 seek 阻挡的定位。共用时钟在目标已一致时不再次写 currentTime，避免 seeked 触发无限定位。播放器身份与图片显示状态均属于界面，不进入时间线、撤销或正式导出。

## Alternatives considered

- 移动片段或新增黑幕修复定帧：该接点已有完整覆盖，修改工程不能修复播放器加载生命周期。
- 保留所有 clip.id 播放器并预加载整段工程：大量素材将同时持有解码器和内存，规模随片段数增长。
- 只保留旧精确帧：可以遮住暂停时的黑屏，但连续播放仍会重建视频，跳过的 seek 也不会追到最终位置。

## Consequences

监视器最多保留一张已加载精确帧和一张当前请求，不积累历史图像，也不引入 Blob URL。真正的黑帧、画面空隙、颜色片段和视觉转场照常显示；加载中暂留上一时刻画面并提供状态反馈。官方操作指南、技术解释、旁置画板和阅读简介同步维护，管理员已导入的文档不自动回写。

没有公共 API、数据库迁移或真实时间线写入。此前的源帧采样修复仍由共享媒体渲染能力独立拥有，见 [源帧采样 Note](2026-10-07-video-editor-source-frame-sampling.md)。

## Verification

组件回归覆盖延迟图片交接、快速前后定位的过期响应、请求失败、真实黑帧替换、连续接点播放与暂停复用、版本与工程隔离、seek 结束后的最终定位、跳剪、真实空隙与同时参与转场的独立播放器。

327 项编辑器 Web 测试、4 项官方知识库组件测试和 48 项架构测试通过。真实 Chrome 浏览器在全新隔离账号与工程中验证：阻塞精确帧请求期间旧帧保持可见、快速前后定位最终只显示最新请求、连续接点播放保持同一个 HTMLVideoElement、源跳剪独立定位、真实空隙与纯黑片段正常显示。浏览器测试通过现有官方 API 创建和清理测试项目，数据库与产物均位于 `.local/video-editor-seam-preview/`。
