# Agent Note: 素材预处理与视频导出独立调度

Status: implemented

## Problem

视频编辑器原来只有一个串行后台轮询器，素材预处理、整片导出、分段导出与素材烘焙共享排队顺序。整片导出运行时，新上传素材一直显示“等待处理”。真实工程中一个 running render 从 67% 推进到 82% 时，新上传 18-v3 的 media 任务仍为 queued 且 started_at 为空，确认是调度阻塞。

## Decision

`VideoEditorRunner` 显式区分 media 与 export 两个调度通道，应用装配分别注册实例。media 通道只处理代理、缩略图和音频波形准备；export 通道处理整片导出、分段导出和素材烘焙。每个通道串行执行自己的任务，最多同时执行两项工作，使用独立短事务和媒体处理会话。启动恢复只重新排队本通道的 running 任务，不影响另一通道；两者都纳入已有 RunnerSupervisor 的启动、停止和健康检查。

上传、重试和任务持久化仍使用原有正式 API。无需 schema 迁移，不新增配置，也不把真实数据库直接写入作为恢复方式。运行中的旧后端仍按原调度执行；这项更改在桌面应用应用后端更新后生效。

## Alternatives considered

优先挑选 media 任务不能打断已经等待中的长导出，仍然要等下一次轮询。一次 gather 导出和预处理也会在导出完成前阻止下一次挑选新上传任务。全队列无限并发会放大 FFmpeg、磁盘与 CPU 压力，因此采用两个独立串行通道。

## Consequences

新上传素材可以在导出过程中完成准备，其他素材仍按各自通道顺序等待。两项本地媒体工作可能竞争 CPU，但不会因已有导出占据唯一轮询器而始终无法启动。真实工程仅只读诊断；不打断用户运行中的导出，也不创建重复处理任务。

- 隔离临时数据库测试阻塞导出处理器，同时完成素材处理，验证导出仍为 running 而 media 已 completed。
- 分别验证两个通道的恢复只修改本通道，export 轮询不认领 media 任务。
- 素材上传、重试、烘焙、特效制作交接与架构测试回归；文档同步独立队列及就绪标志。
