# Agent Note: ZEALMAN 查询异常与执行状态核对

Status: implemented

## Problem

ZEALMAN 的 result/history 查询可能返回 HTTP 500 history request timeout，此时已受理的 ComfyUI 任务仍在实际队列执行。原适配器把查询异常直接抛给任务驱动，驱动将应用任务终结为失败；GPU 作业却仍占用单卡。查询失败不能证明执行失败，也不允许重新提交来恢复。

## Decision

仅在供应商轮询边界将 HTTP 408、429、5xx 或传输异常交给只读核对。台账返回视频或明确执行失败时采用对应终态；队列存在同一任务、不可用队列下台账明确运行，或已完成台账尚在落盘时，返回标准 pending/processing 状态并等待下一轮查询。可读取的空队列优先于过时 running 台账；没有正面证据时保留原异常。鉴权、参数和无效响应错误不走该恢复路径。

核对请求只使用 GET，不重发生成、不修改远程任务、不改共享状态机、REST/SSE 或数据库契约。终态回收原有实时监视器；等待状态保留监视器。当前已被终结的应用任务不会靠本代码自动复活，晚到视频须通过正式素材与输出接口保留，并保存原失败回执。

## Alternatives considered

- 将所有查询异常当 processing：会掩盖失效任务或权限问题，必须有正面执行证据。
- 自动重提或重启服务：可能产生重复付费/并行任务或丢失在途输出，维持现有单次提交与恢复边界。
- 把供应商原始队列暴露到公共状态契约：增加跨层耦合，在适配器内部归一化即可。

## Consequences

暂时查询失败不再将可证实仍执行的任务过早终结。没有证据仍会报错，真实执行错误继续终结；上游长期停滞仍需制作运行器按真实队列观察，不能仅凭本地 failed 推断资源释放。源码修复在当前 GPU 作业结束前不通过重启后端应用，真实长任务恢复与代码单元测试分别记录。
