# Agent Note: Studio 组件归属与分层迁移

Status: implemented

## Problem

网站与独立服务共用业务实现，但原有入口、协议、存储和主机适配散布在 `app` 与多个 `fpl_` 包。业务通过数据库 Session 的信息字典取得依赖，纯编辑规则间接加载 ORM，替换能力时难以明确边界。

## Decision

后端统一采用 `studio` 命名空间。`apps` 按业务所有者组织用例、规则、传输和存储。`contracts` 按协议所有者保存可独立加载的数据契约。`runtime` 保存无业务归属的机制，`config` 拥有配置格式，`host` 拥有主机适配，`assembly` 拥有网站、独立服务与主机的依赖装配，`deployment` 拥有构建工具。

组件显式声明输入、输出、状态归属及失败语义。用例决定事务边界，存储适配提供原子操作。业务规则通过命令、快照和领域错误交互。跨应用消费公开契约，执行器回执由业务所有者裁决。账号、revision、幂等键、取消和未知结果属于接口契约。

前端 `app` 装配，`features` 拥有业务与缓存键，`platform` 拥有浏览器适配，`shared` 拥有通用展示。父包初始化保持轻量。

## Alternatives considered

- 全局按四个技术层集中代码，会使单个业务的生命周期横跨多个全局目录。
- 只删除前缀，无法解决事务、依赖注入和实现类型外泄。

## Consequences

- Python 打包、服务装配和镜像闭包统一引用 `studio`。目录、入口及状态归属由 [项目目录索引](../../../../docs/architecture/project-layout.md) 维护。
- 两种装配选择具体的数据库、素材、模型及主机执行适配。存储负责账号隔离，业务负责事务范围和状态裁决。替换实现使用相同契约场景验收。
- 架构检查覆盖依赖方向、父包初始化、循环依赖和尺寸。移动代码时同时核对入口、源码闭包与部署归属。
- 已登记迁移和持久格式沿用兼容契约。正式数据切换由网站协同会话按维护窗口单独验收。
