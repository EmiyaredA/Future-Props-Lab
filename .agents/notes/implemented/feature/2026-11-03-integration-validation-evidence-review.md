# Agent Note: Review integration validation against durable execution evidence

Status: implemented

## Problem

Integration validation reserves shared Models capacity before an outbound request. If the request is cancelled or its response is lost, its result is unknown and the reservation must remain. Previously the account had no view of pending attempts or explicit way to retry settlement after native evidence arrived. Treating a timeout, expired lease, or a user's declaration as proof of termination risks releasing quota while external work is still active.

## Decision

The owning account can list pending validation attempts and ask to check one original receipt. The API exposes only a bounded paginated account-scoped status, integration ID, type and creation time, never original input or credentials. The Integrations page shows the status and provides a receipt-check action; it neither retries the tool nor claims that unconfirmed work has ended. The operation requires the existing `configuration.manage` permission and cross-account IDs return 404.

For an unknown native MCP discovery, settlement is permitted only if its own persistent job has a terminal outcome receipt, or if it was cancelled before any worker acquired it. The job must match the original intent ID, owner, connection revision and input digest. These checks occur with the attempt status transition in one local short write transaction. Repeated and concurrent requests use the same Models capacity receipt. A confirmed but temporarily unavailable release remains in the existing settlement outbox for retry.

Unknown remote HTTP work and native jobs without a durable terminal receipt remain unknown and retain quota. An unknown execution receipt itself does not prove the underlying external process ended. The page says why no release occurred; it does not offer an unsafe manual override.

## Alternatives considered

- Release on timeout, lease expiry, or after an account acknowledgement: none proves the remote process stopped and can oversubscribe active capacity.
- Retry the original outbound request: a lost response cannot distinguish an action that already happened from one that never started.
- Expose internal worker payloads or credential-bearing inputs to identify attempts: the account only needs non-sensitive connection and timing metadata.

## Consequences

A current authorized account can inspect and reconcile known terminal evidence without changing the original external action. Remote results with no reliable evidence still require a future verified stop/termination protocol; this change does not claim that such reservations can always be recovered. Removing that uncertainty requires evidence from the corresponding execution boundary, not elapsed time or a user statement.

## Verification

Isolated Integrations database checks cover account isolation, unknown remote and active native jobs, terminal native evidence, altered input digests, concurrent/repeated settlement and unavailable Models settlement followed by retry. UI checks cover receipt review, retained unknown quota and paging. Public schemas and SDK are generated by the central contract workflow; no formal data or live external service is used.
