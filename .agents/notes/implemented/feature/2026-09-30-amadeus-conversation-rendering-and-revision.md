# Agent Note: Amadeus 对话分层渲染与可修订产物

Status: implemented

## Problem

Amadeus 将每次工具调用铺在主对话中，长任务的结论、审批与执行证据混在一起。计划和内容草稿只是普通文本，用户无法在卡片中修改后请 Agent 继续。待批准操作的参数与哈希绑定，直接改写原提案会使审批含义失效。

## Decision

展示层从已保存消息、运行事件、提问和操作构建独立时间线，模型历史仍使用原始记录。主对话展示答复、里程碑、计划／草稿与写入审批；工具细节放在自适应执行详情栏。`present_artifact` 是只展示内容的结构化 Agent 工具，使用已有 `tool_call` 和 `tool_result` 事件持久化，无新表或公共事件种类。Plan 输出步骤，草稿输出正文；旧纯文本计划仍可回看和修订。

用户修改计划或草稿后，改动作为新用户消息进入同模式的来源运行续接，旧版本保留。写入参数修订先按原哈希撤回旧审批，再把完整参数草案交给 Agent 重新读取和拟案；浏览器不会直接执行编辑后的参数。已完成 Plan 可续接 Plan 或 Agent，已完成 Agent 可续接 Agent；来源运行仍只能被使用一次。

## Alternatives considered

- **从回答文字猜测草稿类型** — 不改变 Agent 工具，但普通答疑容易被误识别，历史消息的展示也会随规则变化。
- **直接覆盖原计划或审批参数** — 交互步骤少，但破坏历史依据；审批哈希不能代表用户实际批准的参数。
- **新增产物表和消息元数据** — 能提供更细的版本关系，但当前来源运行链和既有事件已足以追踪修订，新增迁移没有必要。

## Consequences

- **收益**：纯问答保持简洁；工具和子任务可追溯；计划、草稿与写入提案都能通过用户反馈重新生成。
- **代价与已知上限**：结构化卡片依赖模型调用 `present_artifact`；未调用时 Agent 文本照常显示。来源运行的一次续接限制保留，用户需从最新版本继续。

## Verification

运行 `uv run pytest tests/test_amadeus_workflows.py -q`、Amadeus Web 组件测试、桌面隔离烟测、Lint、格式和构建检查。覆盖来源运行唯一性、编辑反馈、审批撤回、新提案与未知结果不重试。
