# 时间线与媒体渲染：从状态到帧

剪辑窗口在第 2 秒显示正确，导出视频的声音却提前了半秒。这个问题无法只靠比较截图解决，因为画面和音频都要从输出时间映射到各自的素材时间。

以两倍速片段和一个转场为例：渲染器先判断当前时刻有哪些片段生效，再映射源时间、采样素材、应用效果并合成。最后编码得到文件。时间线是这套求值的输入，不是已经生成好的视频。

## 视频帧与音频共同组成输出

一份渲染计划为什么要同时约束画面与声音？

```fpl-canvas
rendering
```

图例：中央上下两条路径分别处理画面与声音，右侧汇合成输出。此图描述职责而非承诺并行线程；输出需要两条时间语义一致，静帧正确不能证明音画同步。

上路生成视频帧，下路采样与混合音频，二者都以成片时间为基准。编码器负责组合输出，但不能修正上游已经算错的源时间。双路图表示语义依赖，不承诺实际实现一定使用并行线程。

## 输出时刻到源采样

给定时刻 t，渲染器怎样确定从哪个素材位置取样？

```mermaid
flowchart LR
  T[输出时刻 t] --> C[确定活动片段]
  C --> S[映射源时间]
  S --> F[采样画面与音频]
  F --> E[应用效果与转场]
  E --> O[组合输出帧]
```

图例：每个方框是一次语义变换，箭头表示输出供下一阶段使用。t 是成片时间，不是素材时间；多个活动片段可以共同参与同一帧的转场求值。

先找到活动片段，扣除片段的时间线起点，再按速度映射到源区间。转场期间可能同时有多个活动片段，它们按相应权重共同贡献输出。字幕、图层和效果也必须在同一个输出时刻求值。

## 为什么渲染能力由公共模块拥有

视频剪辑、Galgame 路线输出与特效交付会遇到相同的时间与素材语义。公共媒体能力拥有确定性求值与输出实现，各应用负责把自己的工程转换成明确输入。Galgame 的直接视频导出因此不需要导入视频编辑器内部用例。

共享的目标是让相同描述产生一致结果，并不意味着所有预览与成片都共用完全相同的显示设备或编码器。浏览器预览、静帧和最终视频仍要通过共同用例与边界测试核对。

## 预检和验收检查不同的事

预检应发现缺失素材、无效区间和不支持能力。输出验收还要查看起止帧、接缝、速度变化后的源位置，以及对白与声音的对应。仅检查文件存在或时长大致正确，会漏掉时间映射错误。

渲染失败时保留原工程和明确错误；中途产生的部分文件不能作为完整成片交付。复杂工程仍受本机算力、内存、编解码和素材兼容性约束。

> [!TIP]
> 挑选“片段第一帧、转场中点、片段末帧”作为检查点，再试听同一时段的声音，通常比随机截取一个中间帧更容易发现边界错误。
