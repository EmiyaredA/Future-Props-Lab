# 测试与交付证据

画板按钮已经能点击，能否就宣布功能完成？还不能。后端可能拒绝保存，备份可能漏掉图片，Markdown 导入可能丢元素，桌面安装包也可能没有包含懒加载图形资源。

以“新增 canvas 笔记节点”为例，本篇说明如何沿数据路径选择检查。不同测试回答不同问题，局部通过不能替代完整交付证据；全仓已有失败也不能不加区分地归到新功能上。

## 发布验证的四类证据

哪些证据需要同时成立，才能支持“这份功能可以交付”？

```fpl-canvas
engineering
```

图例：四张证据卡并列描述不同检查目的，无箭头的连线表示检查之间的联系，右侧是共同支持的交付结论。局部通过不能代替全部门禁，已有失败也需要注明。

契约检查确认前后端与 SDK 使用一致接口；结构检查确认依赖和权限登记；行为测试确认操作结果；构建资源检查确认真实产物可运行。它们互相联系，但任何一项都无法独自覆盖另三项。

## 建议的验证顺序

从哪里开始验证，能更快发现错误而不反复运行全部测试？

```mermaid
flowchart LR
  A[修改功能] --> B[单元与协议测试]
  B --> C[契约与架构检查]
  C --> D[构建与资源检查]
  D --> E[隔离环境浏览器验收]
  E --> F[记录结果与限制]
```

图例：方框给出从局部测试到交付检查的顺序建议，不是自动执行的 CI 图。失败要回到相应层定位；最后记录实际跑过的范围和未验证限制。

先验证最靠近改动的纯函数与协议边界，再检查跨层契约，最后在隔离环境操作打包产物。遇到失败回到对应层定位；修复后重跑受影响范围，而不是靠重复同一条成功检查增加信心。

## 为画板建立一条可复现闭环

内容校验要覆盖无效版本、悬空连线、非法素材引用；组件测试要覆盖场景编辑与错误反馈；API 测试要覆盖保存、历史、权限和跨账号拒绝。可移植测试需要真实地导出再导入，比较元素、连线和图片重映射。

浏览器验收再验证用户能找到入口、窄屏能操作、保存失败后草稿仍在，以及只读账号没有写入入口。离线验证应阻断外部网络后重新打开尚未加载的文章，而不是只查看已经缓存过的一页。

## 接口与生成物必须一起演进

公共接口变化由统一的 OpenAPI/SDK 生成流程传播，不能手工修生成文件来制造通过。新增路由同步登记权限和响应式覆盖；目录职责变化更新结构索引；用户行为变化更新知识库版指南。

Agent Note 解释工程决策和验收证据，用户指南解释如何完成任务。既有受保护文档中心继续保留，不能为了整理工程说明而重写或迁走。

## 报告实际结果，而不是笼统的“测试通过”

记录运行范围、隔离方式和失败原因。缺少真实供应商凭证时说明未验证的网络路径；用固定数据测试错误语义。二进制资源还要确认是实际 Git LFS 对象，指针文本或校验和不一致都不算可用素材。

> [!NOTE]
> 构建成功只证明这次构建完成。需要交付离线功能时，还要检查产物包含资源，并在断网条件下实际打开相应功能。

## 为三条数据流建立不同证据

| 场景           | 核心验收                           | 失败分支                       |
| -------------- | ---------------------------------- | ------------------------------ |
| 带图片画板保存 | 版本推进、图结构和图片可重新读取   | 409、非法引用、本机草稿恢复    |
| 图片生成       | 输入与任务固定，结果托管后可再引用 | 提交中断、缺结果地址、落盘失败 |
| 视频输出       | 工程快照、预检指纹、时间与音画对应 | 预检过期、素材未就绪、部分输出 |

三个闭环都需要正常结果，但各自的状态和恢复不同。用供应商固定事件验证任务规则，用实际解码的输出验证渲染边界；不能把“有任务记录”当作已经得到成品。

## 从测试报告追到实现依据

内容测试核对标题、链接、源码入口和图形；组件测试核对焦点、错误和视口；API 测试核对权限、版本和事务；浏览器测试核对导航、离线资源与个人副本。报告记录实际运行命令与失败来源，保留既有改动，不为了让全仓绿而修无关模块。契约生成链在专门文章展开，行为证据仍需独立成立。
